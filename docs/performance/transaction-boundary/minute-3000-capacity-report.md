# 1분 3,000건 수용량 단계 테스트

## 결론

`1분간 3,000건`, 즉 평균 50 RPS를 기존 답변 60%, 5~10초 Mock RAG 신규 질문 40%로 구성해 단일 로컬 인스턴스에서 검증했다. Tomcat 200→250→300, Hikari 20→30→40을 단계적으로 조정했지만 모든 조합이 성공 기준을 충족하지 못했다.

- 스레드를 늘릴수록 Tomcat busy와 JVM live thread가 설정 한도까지 증가했으며 시스템 CPU는 모두 100%에 도달했다.
- Hikari 40에서는 pending이 0이 됐지만 성공 요청 수는 늘지 않았다.
- 모든 실행에서 Hikari acquisition timeout과 MySQL max-connection rejection은 0이었다.
- 따라서 이 조건의 지배적 병목은 커넥션 풀 크기가 아니라 5~10초 외부 호출 동안 플랫폼 스레드를 점유하는 동기 MVC 구조와 로컬 CPU 한계다.

## 성공 기준

- 정확히 3,000건 선택, dropped iteration 0건
- 기존/신규 요청 실패 0건
- Hikari acquisition timeout 0건
- MySQL max-connection rejection 0건
- 기존 질문 p95 1초 이하, 신규 질문 p95 15초 이하
- 애플리케이션 비정상 종료와 필수 지표 누락 없음

## 1,000 스레드 한계 확인

별도 3,000 VU 단계형 실험에서 Tomcat만 1,000으로 늘리고 Hikari 20을 유지했다. Tomcat busy 997, JVM live threads 1,026, JVM memory-used 합계 약 2.1GB, 시스템 CPU 약 100%에 도달한 뒤 애플리케이션이 응답하지 않았다. 플랫폼 스레드 대량 증설은 안정화 전략에서 제외한다.

## 다음 대안

### 1. API 응답 계약을 유지하는 비동기 MVC 처리

가장 작은 코드 변경 후보다.

1. `ProcessAnswerService`의 `.block()`을 제거하고 `Mono<QuestionResponse>`를 반환한다.
2. Controller도 `Mono<QuestionResponse>`를 반환해 외부 RAG 대기 중 servlet thread를 컨테이너에 반환한다.
3. 초기 검색 트랜잭션은 기존처럼 짧게 종료한다.
4. RAG 완료 후 DB 저장만 전용 bounded executor에서 `TransactionTemplate`로 실행한다.
5. RAG 동시 실행 수, timeout, circuit breaker를 별도의 bulkhead로 제한한다.

이 방식은 클라이언트가 기존과 동일하게 최종 200 응답을 받으면서 외부 대기 중 Tomcat 플랫폼 스레드를 점유하지 않게 한다. 다만 실제 RAG 공급자가 평균 20 RPS, 약 150개 동시 요청을 허용해야 한다.

### 2. 비동기 작업 큐와 202 응답

외부 RAG 동시 처리 한도가 150보다 작거나 응답 시간이 더 길어질 수 있다면 이 구조가 최종 대안이다.

```text
POST /questions
  → 기존 답변이면 200 즉시 반환
  → 신규 질문이면 PENDING 작업 저장 + 202/jobId
  → Queue
  → 제한된 RAG Worker
  → 결과 저장
  → GET /jobs/{jobId} 또는 SSE로 완료 확인
```

MySQL 작업 저장과 Queue 발행의 이중 쓰기는 transactional outbox로 보호하고, 정규화한 질문 fingerprint에 unique 제약을 두어 동일 질문의 중복 작업을 합친다.

## 테스트 한계

- 애플리케이션, k6, MySQL, Mock RAG가 같은 로컬 장비의 CPU를 공유했다. 절대적인 운영 용량 수치가 아니라 설정 간 비교와 병목 판정 근거다.
- 테스트는 정확히 1분간 3,000 iteration을 예약한 것이며 3,000 VU 동시 처리 검증이 아니다.
- 실제 외부 RAG의 rate limit, 동시성 제한, 네트워크 오류는 Mock에 포함하지 않았다.
- 운영 용량 확정 전에는 부하 발생기, 애플리케이션, DB를 분리한 환경에서 같은 테스트를 반복해야 한다.

## 하네스 검증

- Mock RAG, 60:40 선택, minute-3000 프로필, 지표 요약, 실행 계약 Node 테스트: 15/15 통과
- `k6 inspect -e LOAD_PROFILE=minute-3000`: constant-arrival-rate, 50 RPS, 60초 확인

- `./gradlew --no-daemon bootJar`: 통과

## 이력서에 사용할 수 있는 범위

현재 증거로는 `3,000 VU를 안정적으로 처리`했다고 쓸 수 없다. 다음 표현은 사실과 일치한다.

> TransactionTemplate로 DB 트랜잭션과 외부 RAG 호출 경계를 분리하고, 1분간 3,000건이 유입되는 60:40 혼합 부하에서 Hikari timeout 0건을 확인했습니다. 단계형 튜닝을 통해 커넥션 풀이 아닌 동기 요청 스레드와 CPU가 다음 병목임을 식별했습니다.

비동기 처리 변경 후 모든 성공 기준을 통과한 경우에만 `1분간 3,000건 안정 처리`를 추가한다.
